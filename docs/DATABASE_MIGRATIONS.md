# Структура базы и миграции

Qronion использует PostgreSQL и Alembic. Приложение при запуске только
проверяет версию и необходимую структуру БД. Оно не создаёт таблицы
и не применяет миграции автоматически.

## Чистая установка

Установите зависимости из `requirements.txt`, создайте пустую PostgreSQL-базу
и настройте `DATABASE_URL` в `main.env`. Из корня проекта выполните:

```bash
python -m app.schema upgrade
python -m app.schema check
```

После этого можно создавать начальные учётные записи и запускать приложение.
`deploy/install.sh` копирует каталог `migrations` и `alembic.ini`, применяет
миграции и только затем запускает службу. Если миграция завершилась ошибкой,
установщик останавливается. Повторное применение уже установленной версии
не создаёт таблицы заново и не сбрасывает нумерацию талонов.

Начальная миграция рассчитана на пустую базу. Старые базы без Alembic
не переносятся автоматически. Для запланированной переустановки на ВМ
используйте отдельную пустую базу. Не выполняйте `alembic stamp head`
для обхода проверки. Решение о чистой установке записано
в [INSTALLATION_DECISIONS.md](INSTALLATION_DECISIONS.md).

## Последующие обновления

На установленном сервере откройте `sudo qronion` и выберите «Обновить очередь».
Меню само готовит зависимости, останавливает службу, создаёт копию БД,
применяет миграции и проверяет запуск. При сбое используйте пункт восстановления.
Пути к файлам и порядок работы описаны в [README](../README.md#установка-и-обновления-через-меню).

### Ручное обслуживание

Остановите службу очереди, обновите файлы и зависимости. Сделайте резервную
копию БД через `deploy/backup_db.sh`. Выполните `python -m app.schema upgrade`
от пользователя приложения, затем запустите службу. При ошибке оставьте службу
остановленной и устраните причину перед повторной попыткой.

`deploy/update_from_git.py` обновляет только файлы. Он не устанавливает
зависимости, не меняет БД и не перезапускает службу. Резервная копия файлов,
которую он создаёт, не заменяет копию БД.

## Разработка миграций

Начальная структура зафиксирована в `migrations/sql/0001_schema.sql`.
Функция и триггер нумерации находятся в `0001_numbering.sql`.
Эти файлы не зависят от будущих изменений ORM-моделей. Не редактируйте
уже выпущенные миграции. Создавайте новую ревизию:

```bash
python -m alembic revision --autogenerate -m "Describe schema change"
python -m alembic upgrade head
```

Проверьте созданную ревизию вручную: перенос данных, SQL-функции и триггеры
не определяются автоматически. Транзакционная блокировка не позволяет двум
процессам одновременно применять миграции. PostgreSQL откатывает изменения
схемы при ошибке внутри миграции. Начальную схему нельзя удалить через
`downgrade`: это удалило бы данные очереди.

Основа настройки: [руководство Alembic](https://alembic.sqlalchemy.org/en/latest/tutorial.html).

## Часовой пояс очереди

В `main.env` параметр `QUEUE_TIMEZONE` задаёт пояс учреждения, например `Asia/Irkutsk` или `Europe/Moscow`. На новой установке Linux установщик берёт пояс сервера. Для действующей установки без этого параметра используется Иркутск.

Миграция `0002_utc` переводит прежние иркутские отметки времени в точные моменты UTC. Перед обновлением остановите очередь и сделайте резервную копию. Штатное обновление Linux выполняет оба шага автоматически.

Чтобы сменить рабочий пояс, остановите очередь, измените `QUEUE_TIMEZONE`, выполните `python -m app.schema upgrade` и запустите очередь. Для установленной Grafana примените `scripts/syncGrafanaDashboard.py` с правами на запись в папку дашбордов через Python из окружения приложения. Часы, расписание и границы дня будут использовать новый пояс.

Если обновление выполняла предыдущая версия программы обновления, после первого перехода выполните из каталога установки `sudo ./venv/bin/python scripts/syncGrafanaDashboard.py`, чтобы Grafana получила запросы для новой схемы.
